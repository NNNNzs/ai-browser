# 项目代码探索与文档化

你正在帮助用户学习一个项目并准备二次开发。你的任务是深入探索指定模块的代码，将发现整理成结构化的设计文档。

## 工作流程

### 第一步：确定范围

根据用户指定的目标，先快速扫描相关目录和文件，建立模块的边界认知：
- 这个模块包含哪些子目录和关键文件？
- 它与哪些其他模块有交互？
- 复杂度如何？判断产出单篇文档还是多篇。

**粒度判断原则：**
- 简单模块（单文件或少文件）：一篇文档搞定
- 中等模块（多文件、有子目录）：按子模块拆分，每个子模块一篇，加一篇总览
- 复杂系统（跨进程、多层级）：按层/角色拆分，每层一篇，加一篇总览

### 第二步：深度探索

逐个阅读关键文件的源代码，记录：
- 导出/暴露的接口和类型
- 核心数据结构和状态定义
- 关键函数的实现逻辑（不是逐行翻译，而是提炼设计意图）
- 模块间的依赖和调用关系
- 配置项和默认值
- 值得注意的设计决策（为什么这样做）

使用 Agent/Explore 工具进行大规模探索，减少主上下文的压力。

### 第三步：撰写文档

在 `docs/design/<模块名>/` 下创建文档。

**文档结构模板：**

```markdown
# <模块名称>

> 一句话说明这个模块是什么、做什么。

## 概览

模块的整体定位和职责。用 mermaid 图展示模块在系统中的位置或核心架构。

## 目录结构

\```
<模块路径>/
├── file-a.ts    # 简要说明
└── file-b.ts    # 简要说明
\```

只列出关键文件，忽略不重要的辅助文件。

## 核心设计

### <设计点 1>

设计思路和实现原理。如果涉及数据流或调用链，用 mermaid 流程图。

### <设计点 2>

...

## 数据结构

关键类型定义和接口，附简要说明。

## 与其他模块的交互

用 mermaid 图展示调用关系或数据流向。

## 设计决策

记录非显而易见的设计选择，解释"为什么这样做而不是那样做"。这是对二次开发者最有价值的部分。

## 关键文件索引

| 文件 | 职责 |
|------|------|
| path/to/file | 一句话说明 |
```

### 第四步：更新 CLAUDE.md 索引

在项目根目录的 `CLAUDE.md` 末尾追加设计文档索引区：

```markdown
## 设计文档索引

- [<模块名>](docs/design/<模块名>/) — 一句话简介
```

如果索引区已存在，在其中追加新条目。不要改动索引区以外的内容。

## 写作规范

- **语言**：中文，技术术语保留英文原文
- **图表**：优先使用 mermaid 语法（流程图用 flowchart，架构用 graph，时序用 sequenceDiagram）
- **渐进式披露**：先给全局视图，再展开细节。读者应该能通过小标题快速跳到自己关心的部分
- **面向二次开发**：重点解释"为什么"而不是"是什么"，读者需要的是理解设计意图以便修改和扩展
- **具体 > 抽象**：写真实的文件路径、函数名、类型名，不要用伪代码
- **克制**：不要为显而易见的东西写注释式文档。如果一个组件的职责从文件名就能看出来，一句话带过即可
- **避免**：不要重复 README 或 CLAUDE.md 中已有的内容，用引用代替
